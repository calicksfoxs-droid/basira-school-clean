# بصيرة — البنية الأساسية V1

## القرار المعماري

يستمر المشروع كتطبيق Next.js واحد بطبقة وصول بيانات خادمية واحدة، ووضعي Demo وSupabase متكافئين وظيفياً. لا خدمات مصغرة ولا تطبيق ثانٍ ولا مخزن متصفح للبيانات الإنتاجية.

## النموذج المعتمد

```text
Teacher
  └─ LearningSubject
       ├─ SubjectBanner (one active record/value set)
       ├─ SubjectGroup[]
       │    └─ active student memberships
       └─ SubjectUnit[]
            └─ UnitLesson[]
                 ├─ direct content OR one-level parts
                 ├─ private assets
                 └─ optional quiz
```

العضوية في المجموعة تمنح الطالب قراءة المادة المنشورة ووحداتها ودروسها المنشورة. لا تُنسخ المادة لكل مجموعة؛ المجموعة تحدد جمهور المادة فقط.

## الانتقال من الهيكل الحالي

الهيكل الحالي `Group -> Subject -> Lesson` يبقى مؤقتاً لتشغيل الواجهة القديمة حتى المرحلة الرابعة. الترحيل الإضافي يضيف:

- مالكاً مباشراً للمادة.
- ارتباط المجموعة بمادة.
- جدول وحدات.
- ارتباط الدرس بوحدة مع الحفاظ على ارتباط المادة للتوافق.
- مراجع انضمام مستقلة للطلاب.
- إعدادات عامة وتفضيلات شخصية.

السجلات القديمة تظل قابلة للقراءة. الإنشاء الجديد يستخدم الهيكل الصحيح فقط. إزالة أعمدة التوافق مؤجلة لما بعد انتقال الواجهة والتحقق من البيانات.

## حدود الثقة

- Server Actions طبقة نقل رفيعة تعيد التحقق من الهوية والمدخلات.
- طبقة البيانات `server-only` تطبق الملكية وتعيد DTOs محدودة.
- RLS يعيد تطبيق العزل نفسه داخل PostgreSQL.
- استخدام service role مقصور على إنشاء الحسابات والتدفقات التي سبقتها صلاحية صريحة، مع أقل بيانات مرتجعة.
- كل معرف قادم من رابط أو نموذج غير موثوق ويخضع للتحقق والملكية.

## الأداء

- لا استعلام شامل لجميع الطلاب للمدرس.
- قوائم المواد والمجموعات والوحدات مفهرسة بالمالك والأصل والترتيب.
- رحلة التعلم إسقاط مشتق عند الطلب ولا تضيف مزامنة أو عاملاً خلفياً.
- لا رسوم أو تحليلات أو مهام دورية في قلب V1.
